## Objetivo
Integrar el núcleo con **API real de OpenCode 2.0.32** para un único writer sobre un *fixture sintético desechable*. Autoridad aprobada y digest reales, preflight Git/consumidores, reserva antes del despacho, identidad exacta y cierre limpio. No integrar reviews ni correctores aún; son M3.

## APIs verificadas localmente sin IA
En servidor privado OpenCode v2: `POST /api/session` acepta `{title,agent}` y devuelve ID, agent, projectID, title y `location.directory`. `GET /api/session/:id` retorna esos datos; `GET /api/session` lista sesiones (GLOBAL, no asumir local); `GET /api/session/active` y `GET /api/session/:id/message` funcionan. En ensayos previos `POST /api/session/:id/prompt` acepta `{text}` como llamada de trabajo. Estas interfaces están verificadas en CLI 2.0.32, no afirmamos compatibilidad con otras versiones.

## Preflight obligatorio sin modelo
- La autoridad WO debe existir en checkout, calcular SHA256 de bytes EXACTOS y compararlo con `manifest.authorityDigest`. No inferir firma humana a partir de SHA.
- Manifest M1 válido, `BASE==HEAD` y árbol Git limpio. Store fuera de raíz real del repo, sin symlink. `allowPaths` y `doNotTouch` sin solapes.
- `consumerSymbols` NO vacía para el test vivo. Resolver nombres de consumidores en Git BASE con `git grep -w -F`; todos los archivos reales identificados deben estar en allowPaths o doNotTouch. Si falta un consumidor → `BLOCKED_PREP`. Marcar `G03_PASS_DECLARED_SYMBOLS`, nunca cobertura universal.
- Host URL loopback; no pasar URLs externas arbitrarias. Agente `build` exactamente para la prueba. El ejercicio real corre en repo con bandera sintética controlada; sin secretos clínicos, sin tokens de producto, sin deploy.

## Despacho
1. Antes de llamar al host generar marcador de correlación aleatorio y **persistirlo dentro del evento duradero `RESERVE_WRITER`**, sujeto a CAS del store. Un evento repetido devuelve `WRITER_ALREADY_RESERVED`, nunca crea segunda sesión.
2. Crear sesión `POST /api/session` con título marcador. Respuesta no concluyente → solo lectura `GET /api/session`, filtrar título exacto, `location.directory`, `projectID`, agent, y verificar `GET /api/session/:id`. 1 coincidencia completa = se puede reconciliar; 0 o >1 / host no accesible = `HUMAN_STOP` sin nuevo POST.
3. Después de validar identidad y session ID, persistir `HOST_CONFIRM`, luego **enviar un único `POST /api/session/:id/prompt`** con texto acotado. No reintentar POST ambiguo. El prompt no genera autoridad nueva ni permite publicar.
4. Comprobar candidato Git `HEAD != BASE`, parent EXACTO base, árbol limpio, archivos modificados dentro de allowPaths y ninguno bajo doNotTouch. Solo entonces `CANDIDATE_CREATED`. En M2 no consumir `WITNESSES_PASSED` ni simular reviews; `CANDIDATE` es límite de M2.
5. Probar un fallo inyectado entre reserva y creación: la segunda invocación nunca crea otra sesión. Probar respuesta de create perdida, sesión con título ajeno/duplicada, respuesta prompt ambigua y estado de host. No atribuir garantía exactly-once: SOLO reserva at-most-once, un envío por run y STOP seguro.
