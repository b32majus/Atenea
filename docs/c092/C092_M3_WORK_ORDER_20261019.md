# C-092 · M3 — Contrato de integración de testigos, revisión y corrección
**Autoridad:** arquitectura C092 (M0), M1 auditado `01716d8`, M2 nativo `d8e3290`. Rama aislada, **solo fixture sintético**, sin merges, push ni despliegue.

## Entregables M3 y condiciones de entrada
1. **Testigos deterministas:** lista tipada pre-aprobada por operador (no argv del modelo), ejecutada sobre **Git checkout limpio detached del candidato**. Registrar argv, SHA revisado, exit code, stdout/stderr, hashes y errores; fallo o falta de un testigo = HUMAN_STOP, nunca PASS. No usar shell; env minimizado. No dejar directorios o procesos testigo vivos tras cierre.
2. **Standards y Spec independientes** sobre el MISMO SHA, sesiones nuevas de OpenCode, título con correlación/axis/SHA/attempt y roles de solo lectura. **Visual obligatorio** cuando manifest UI=quality/fidelity, no cuando uiImpact=none. Verificar host (id, agent, projectID, directory, título). Toda revisión retorna JSON tipado: `axis,sha,status,findings[]`. Un estado PASS requiere findings=[], ruta y evidencia completas para findings reales. Prohibido confiar en un recibo de sesión como PASS.
3. **Cierre:** una sola review por eje/commit. Reutilizar receipts fijos, no repetir. Si todos PASS, verificar host/Git/testigos del candidato y transicionar a READY_FOR_HUMAN. Si hay defects, agrupar IDs únicos y prescripciones inequívocas para **un corrector nuevo**. Si hay conflicto de eje o resultado ambiguo: HUMAN_STOP, no decidir por heurística.
4. **Corrección:** máximo dos slots de M1, reservar antes de crear nuevo corrector. El corrector edita exclusivamente la allowlist y entrega un nuevo commit único cuyo parent es el SHA recién revisado, después de testigos reejecutados y cierre focal por ejes afectos (más control de no regresión del resto). No tercer writer. Si la ejecución falla ambiguamente, no recuperar slot ni volver a despachar.
5. **Registro por evento:** adjuntar recibos sha256 de tests/reviews; checkouts privados aislados. Ninguna modificación en producto LAB/PSURE ni C090; ningún agente Build gobierna fases.

## Plan de implementación acotado
- M3-A: paquete testigos + validación de dictámenes + falsadores (sin modelos) hasta suite PASS.
- M3-B: host de revisores reales READ-ONLY contra fixture sintético. Cierre PASS solo tras comparar SHA y reportes. Si no puede demostrarse solo lectura, STOP.
- M3-C: reserva y corrección focal de fixture, testigos y cierre. Solo después de acreditar M3-B. No combinar una incidencia del host con corrección de producto.
- M3-D: auditoría independiente y documentación de garantías faltantes M4.

## Paradas expresas
Ni `WITNESSES_PASSED`, `REVIEW_CLEAN` ni `FOCAL_RESOLVED` pueden derivarse de texto del coordinador, de un archivo manuscrito o de una sesión sin informe validado. La CLI de M1 `advance` **permanece instrumento de laboratorio**.
M3 no solventa todavía M4 (crash/recovery real, sandbox, journal resistente a alteraciones, permisos multiusuario). No probar con proyectos clínicos, datos personales ni producción.
